同一道题可能生成很不同的作品。比较它们之前，首先需要知道自己在比较什么。

今天的 [鹈鹕实验](/blog/experiments/pelican-2026-09-27) 留下了三份独立 3D 场景，以及若干 SVG 习作。整理这些材料时，有几个容易混淆的层次值得分开。

## 四层记录

| 层次 | 应当保留什么 | 不能据此推出什么 |
| --- | --- | --- |
| 任务 | 提示词、约束、输入与工具环境 | 相同标题不代表所有实验条件相同 |
| 产物 | 源码、依赖版本、资源与文件哈希 | 文件更大不代表作品更好 |
| 验证 | 语法检查、页面加载、操作与错误 | 语法通过不代表所有游戏机制正确 |
| 观察 | 视觉感受、交互细节、需要继续检查的问题 | 一次主观体验不是统计显著的模型排名 |

## 不把复制件算成新测试

网页、网页的 ZIP 包和截图可能都来自同一份实现。判断是否独立，不能只数文件：还要比较结构、资源与内容哈希。

```bash
# 比较的是内容，而不是文件名或修改时间。
sha256sum index.html
```

这次三套 3D 场景各有不同源码结构，属于三份独立实现；其中一套的 ZIP 内 HTML 与原页面一致，因此只算一次。

## 让作品可以重新打开

临时域名和 CDN 会变化。把依赖与静态资源一起保留，通常比只留下一个公开链接更可靠。修改资源路径时应记录变化，但不必把迁移副本当成新的生成结果。

## 把尚未知道的事也写下来

有一条叠罗汉图片生成记录尚未找到本地图片。它应当作为“缺失产物”的记录保留，而不是补造图片或从计数里悄悄消失。

同样，来源模型名如果只是日志里的标签，就应该这样描述。诚实的边界会让后续复查更容易。
